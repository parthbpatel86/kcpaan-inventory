# Audit: v1.5.0 backend — verified against the LIVE Neon database (2026-08-15)

Purpose: prove each backend rule Parth specified actually behaves correctly,
with raw request/response evidence. All tests run against the deployed service
(https://kcpaan-inventory-api.onrender.com), not a local stub.

## 1. A1 CRITICAL — timezone bug, proven then fixed

Before the fix, `date(col,'localtime')` was translated to plain `(col)::date`
on the Postgres path, which uses the server's UTC day. Evidence from live data:

```
UTC now   : 2026-08-15 06:48:19+00
Shop now  : 2026-08-14 23:48:19        (America/Los_Angeles)
Shop today: 2026-08-14   <-- correct business day
UTC today : 2026-08-15   <-- what the OLD code used

sale | created_at(UTC)     | shop_day   | utc_day    | total
   1 | 2026-08-15 00:25:51 | 2026-08-14 | 2026-08-15 | 20.0  <-- MISATTRIBUTED
   2 | 2026-08-15 00:30:37 | 2026-08-14 | 2026-08-15 | 41.0  <-- MISATTRIBUTED
   ... all 9 sales mis-attributed
```
Parth's two real sales (5:25pm and 5:30pm Pacific on Aug 14) were being counted
as Aug 15 revenue. This would have made the new closing-shift report wrong on
day one. Fixed by converting AT TIME ZONE SHOP_TZ (env-overridable).

## 2. A4 — stock guard (cannot oversell)
```
$ POST /api/sales {"items":[{"product_id":1,"qty":999}]}   (only 8 in stock)
{"error":"insufficient stock","items":[{"available":8,"id":1,"name":"120 Plus","requested":999}]}
```
Previously this drove shop_qty negative.

## 3. Discount cap — 10% of cart, enforced server-side
```
$ POST /api/sales {"items":[{"product_id":1,"qty":1}],"discount":50}   ($20 cart)
{"discount":2.0,"subtotal":20.0,"total":18.0}
```
Asked for $50 off a $20 cart -> capped to exactly $2.00 (10%). The client can
never over-discount because the server recomputes it.

## 4. Employee 8% — applies, and does NOT stack
```
$ POST .. {"employee_discount":true}                 -> {"discount":1.6,"total":18.4}
$ POST .. {"employee_discount":true,"discount":2}    -> {"discount":1.6,"total":18.4}
```
8% of $20 = $1.60. Passing an extra $2 manual discount changes nothing, exactly
as specified ("no" to stacking).

## 5. Idempotency — a retried sale cannot double-charge
```
$ POST .. {"client_ref":"test-cap-1"}  -> {"id":12, ...}
$ POST .. {"client_ref":"test-cap-1"}  -> {"id":12, "duplicate":true, ...}
```
Same sale id returned; no second sale, no second stock decrement. This matters
because the offline queue retries sales after an outage.

## 8. The 14-hour rule (forgot to punch out)
Seeded a punch-in 20 hours old with no punch-out, then punched again:
```
{"action":"in","employee":"Suresh","warning":"previous shift was not closed — manager must fix"}
```
Timesheet then shows the stale row flagged for the manager:
```
{"id":3,"flag":"MISSING_OUT","punch_in":"2026-08-14 11:01:29+00","punch_out":null}
```

## 9. Manager edit + audit log (3-month retention)
```
$ PUT /api/punches/3 {"punch_out":"2026-08-14T19:30:00","note":"...","changed_by":"manager"}
  -> {"ok":true}
$ GET /api/punch-audit
  field=punch_out old=None new=2026-08-14T19:30:00 by=manager at=2026-08-15 07:01:52
  field=note      old=None new="employee forgot to punch out; confirmed 7:30pm"
```
Every field change is recorded with old value, new value, who and when.

## 10. Close shift — two counters, expected cash, variance
```
$ POST /api/shift/close {"paan_cash":30,"tobacco_cash":15}
{"business_date":"2026-08-15","counted_cash":45.0,"expected_cash":59.0,
 "over_short":-14.0,"cc_total":20.0,"shop_total":0}
```
Expected cash is derived from that day's actual recorded sales; CC and SHOP are
summarised separately. `GET /api/shift/closes` lists previous days with NO
all-time cumulative total (owner-only, per Parth).
