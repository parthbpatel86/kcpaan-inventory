## 1. Backend contract — verified live (not assumed)

```
$ curl -s https://kcpaan-inventory-api.onrender.com/api/health
{"ok":true,"service":"kcpaan-inventory"}
HTTP:200

$ curl -s https://kcpaan-inventory-api.onrender.com/api/employees/faces
[]
HTTP:200
```

Endpoint exists and is live; empty because nobody is enrolled yet.

Read from `backend/app.py` (NOT modified by me):

- `PUT /api/employees/<id>` whitelist is `("name","pin","active","finger_id","face_data")` (app.py:660).
- `GET /api/employees/faces` returns `{id, name, vectors}` for `active = 1 AND face_data IS NOT NULL` (app.py:672-692).
- `POST /api/punch` (app.py:695-712):
  ```python
  emp_id = d.get("employee_id")
  method = "face" if (emp_id and not pin) else "pin"
  ```

**Consequence that drove the client design:** to get `method='face'` recorded, the request
must send `employee_id` and MUST NOT send `pin`. The pre-existing `api.punch(pin, intent)`
always sends `pin`, so a separate `punchByFace()` method was added rather than overloading it.

## 2. Why NOT a full ArcFace/ONNX pipeline — evidence

### 2a. expo-camera 56 has no face detection (checked, not assumed)

```
$ grep -rn "onFacesDetected\|FaceDetector\|faceDetect" node_modules/expo-camera/build/
(no matches)

$ grep -n -i "face" node_modules/expo-camera/build/Camera.types.d.ts
461:export interface CameraViewRef        <-- only hit is the word "interface"
```

`takePictureAsync` DOES support `base64` and `quality` (Camera.types.d.ts:99-108).
`scale` / `imageType` are annotated `@platform web`, so they are no-ops on Android.

### 2b. onnxruntime-react-native is genuinely close, but needs a patch nobody has merged

```
$ npm view onnxruntime-react-native version   -> 1.24.3  (published 2026-07-16, actively maintained)
$ tar -tzf onnxruntime-react-native-1.24.3.tgz | grep unimodule
package/unimodule.json          <-- STILL SHIPS
```

Verified against the live GitHub API (not from memory):

```
$ curl .../issues/29004  -> "[Mobile] unimodule.json makes Expo exclude onnxruntime-react-native
                             from autolinking — NativeModules.Onnxruntime is null"
                             state: closed / completed, author danielweinmann
$ curl .../pulls/29005   -> "Remove unimodule.json so Expo autolinks onnxruntime-react-native"
                             state: OPEN, merged_at: None      <-- fix NOT released
```

Issue #29004 body contains a third-party report that inference works on
**Expo SDK 56 / React Native 0.85 / ORT 1.24.3 on Android** after deleting `unimodule.json`.
So ONNX is *achievable*. It is not *verifiable here*, because:

- the fix is unreleased -> requires adding `patch-package` (not currently in this repo:
  `grep -n "patch-package\|patches" package.json` -> no output), and
- registration happens through RN autolinking into `PackageList.java`, which is a **Gradle
  build artifact**, and running Gradle is forbidden on this machine (16GB RAM, concurrent
  emulator).

Proof that PackageList is a build artifact and is currently stale:

```
$ find android -name PackageList.java
android/app/build/generated/autolinking/src/main/java/com/facebook/react/PackageList.java
$ grep -n "new .*Package()" .../PackageList.java
  AsyncStoragePackage, ExpoModulesPackage, SafeAreaContextPackage, RNScreensPackage, RNCMaskedViewPackage
```

Note `expo-camera` is absent from that list — because it is a first-party **Expo module**
(`node_modules/expo-camera/expo-module.config.json` exists) registered via
`ExpoModulesPackage`, needing no patch. `onnxruntime-react-native` has **no**
`expo-module.config.json`, so it depends on the patched RN-autolinking path.

### 2c. @react-native-ml-kit/face-detection: detection only, and build-risky

```
$ npm view @react-native-ml-kit/face-detection version  -> 2.0.1 (last modified 2025-09-01)
$ grep -n "class FaceDetectionModule" package/android/.../FaceDetectionModule.java
35:public class FaceDetectionModule extends ReactContextBaseJavaModule {
```

Public API (from `package/index.ts`) is `detect(imageURL, options): Promise<Face[]>` returning
`frame`, `rotationX/Y/Z`, optional landmarks/contours/probabilities, `trackingID`.
**There is no embedding/descriptor field** — so it can confirm a face is present but can never
answer "which employee is this". Insufficient alone, per the brief.

### 2d. Expo does not pin any of these for SDK 56

```
$ curl -s https://api.expo.dev/v2/sdks/56.0.0/native-modules | ...
onnxruntime-react-native            -> NOT PINNED BY EXPO
react-native-vision-camera          -> NOT PINNED BY EXPO
@react-native-ml-kit/face-detection -> NOT PINNED BY EXPO
expo-face-detector                  -> NOT PINNED BY EXPO
expo-image-manipulator              -> ~56.0.24     <-- first-party, supported
expo-file-system                    -> ~56.0.9
```

**Decision:** ship a pure-JS embedding using only Expo-supported modules. It adds zero native
modules, so it cannot break the Gradle build that another process owns. It is
verification-grade, not identification-grade, and the UI is built to reflect that
(suggest + one-tap confirm). ONNX is documented in FACE_SCAN.md as the upgrade path;
`embed()` is the only function that changes.

## 3. Dependency install

Pre-existing peer conflict, present BEFORE my change (proof it is not mine):

```
$ npm install --dry-run
npm error ... Conflicting peer dependency: react@19.2.8
  peer react@"^19.2.8" from react-dom@19.2.8   (pulled in via expo-router -> @radix-ui/react-tabs)
  root project has react@19.2.3
```

So `--legacy-peer-deps` was used, matching how `expo-camera` was already installed.

```
$ npx expo install expo-image-manipulator -- --legacy-peer-deps
$ npm ls expo-image-manipulator
kcpaan-inventory@1.0.0
└── expo-image-manipulator@56.0.24        <-- exactly the SDK 56 pin
```

**Packages added: `expo-image-manipulator@~56.0.24` only.** No native module added.
Version numbers in app.json / build.gradle were NOT touched.
